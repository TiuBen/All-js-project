# V5-dispatch 后端部署到阿里云服务器（2026-09-23 核对版）

> 目标：把 `V5-dispatch`（Express + PostgreSQL）发布到阿里云 ECS，供前端 `flight-dispatch-system` 调用。
> 本文是**照着做就能上线**的清单，所有命令均已按当前代码核对。

---

## 〇、上线前必须知道的 4 件事（血泪版）

| # | 坑 | 后果 | 现状 |
|---|---|---|---|
| 1 | `package.json` 的 `start` 原本是 `nodemon server.js`，而 nodemon 没写进依赖，`pnpm install --prod` 根本装不到；`main` 还指向不存在的 `src/server.js` | 服务起不来 | **已修**：`start` 改为 `node server.js`，`main` 改为 `server.js`，补了 `engines.node>=18` 与 devDependencies.nodemon |
| 2 | `src/db/schema.js` 建 `manual_fips` 表时**漏了 `uuid` 列**和 `manual_fips_uuid_key` 唯一索引（`data/schema.sql` 里有） | 靠代码自动建表的服务器上，前端"创建检查单"全线失败（uuid 是航班身份键） | **已修**：建表补列 + `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 幂等迁移 + 唯一索引；已用空库实测（5 表 22 列全对） |
| 3 | `资料/flight_dispatch.sql`（旧的 4MB 导出）**只有 3 张表**：`checklist_records` / `fips` / `flights`，**没有 `manual_fips`、没有 `fresh_air_cargo`** | 导入后前端航班列表（数据源 = `manual_fips`）直接 500 | **已解决**：新增全量快照 `flight_dispatch_full_20260923.sql`（6 表 + 数据，见第二节） |
| 4 | nginx 默认 `client_max_body_size 1m`，而检查项截图上限是 8MB、提交 JSON 上限 10MB | 贴图上传必报 413 | **已解决**：nginx 配置里已加 `client_max_body_size 20m`（见第六节） |

> `V5-dispatch/flight_info.sql` 是 **MySQL / Navicat 导出的 `air.flight_info`**，和 PostgreSQL 这套无关，**不要往服务器传**。

## 一、服务器环境（只需做一次）

```bash
# 1. Node.js ≥ 18（本项目是 ESM + Express 4）
node -v
# 没有或太低：
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt-get install -y nodejs

# 2. pnpm（全局装一次，所有项目共享 store，express 等公共包磁盘只存一份）
npm install -g pnpm

# 3. PM2 进程守护
npm install -g pm2

# 4. PostgreSQL ≥ 13（13+ 内置 gen_random_uuid；12 及以下需 pgcrypto）
psql --version
sudo systemctl status postgresql
```

> 依赖复用说明：本项目是 ESM，`NODE_PATH` 那套对 `import` **无效**；用 pnpm 的全局 store 才是正解，新项目 `pnpm install` 时命中 store 几乎秒装。

## 二、上传后端代码

**要传**：`package.json`、`.env`、`server.js`、`src/`、`data/`（含 `checklists/` 模板 + `uploads/` 目录）、`data/schema.sql`。
**不要传**：`node_modules`（本机是 pnpm 软链，拷过去没用）、`flight_info.sql`。

```bash
# 本地在 V5-dispatch 目录打包
tar -czf v5-dispatch.tar.gz package.json .env server.js src data

# 上传（任选其一）
scp v5-dispatch.tar.gz root@服务器IP:/opt/
# 或宝塔面板 / 阿里云文件管理上传

# 服务器上解压（注意 data/checklists 下是中文目录名，务必保持 UTF-8）
cd /opt && mkdir -p v5-dispatch && tar -xzf v5-dispatch.tar.gz -C v5-dispatch
ls /opt/v5-dispatch/data/checklists      # 应看到 节点保障 / 视频监管 两个中文目录
```

> `data/checklists/` 是后端模板服务（`templateService.js`）在运行期扫描的**真实数据源**，漏了它 `/api/checklists/templates` 会返回空列表。
> `data/uploads/` 是检查项截图落盘目录，**必须存在且可写**（`config/index.js` 会自动创建，但父目录权限要够）。

## 三、导入数据库

用**全量快照** `flight_dispatch_full_20260923.sql`（4.09 MB，含 6 张表与数据）。

```bash
# 本地上传（SQL + 导入脚本放同一目录）
scp 资料/flight_dispatch_full_20260923.sql 资料/import_flight_dispatch.sh root@服务器IP:/root/
```

```bash
# 服务器上（以 root 执行，脚本自动走 sudo -u postgres 免密，全程不用密码）
cd /root
bash import_flight_dispatch.sh
```

脚本会自动：建库 → 预置 pgcrypto → 导入 → 打印各表行数 → **校验 `manual_fips.uuid` 列是否存在**。

**期望的基线行数**（与本地库一致）：

| 表 | 行数 | 说明 |
|---|---|---|
| `fips` | 10300 | 历史航班流量（详情 Dialog 用） |
| `flights` | 10310 | 航班表 |
| `manual_fips` | 8 | **前端航班列表的数据源**，含 `uuid` 列 |
| `checklist_records` | 8 | 已填写的检查单 |
| `fresh_air_cargo` | 1 | 生鲜标记（JSONB） |
| `flight_info` | 203 | 历史遗留表（报文类），后端代码未引用，带上无害 |

> 快照已做**低版本兼容处理**：移除了 pg_dump 18 专有的 `\restrict` / `\unrestrict`，注释了 `SET transaction_timeout`，因此在 PG 13~16 的服务器上也能直接 `psql <` 导入。

> 想在服务器上自己重新导出，别用旧机器上的 pg_dump 客户端跨大版本导；最稳是**客户端版本 ≥ 源库版本**。

## 六、Nginx 反向代理（推荐：前端与 API 同域）

已备好两份配置在 `packages/backend/nginx/sites-available/`：

| 文件 | 用途 |
|---|---|
| **`dd.atc1215.cn.conf`** | ★ 推荐。前端静态站 + `/api/` 反代到 127.0.0.1:5183，前端 `VITE_API_BASE=/api`，**同源不触发跨域** |
| `api.duty.atc1215.cn.conf` | 备选。API 单独子域，前端在别的域名时用，需要配后端 `CORS_ORIGIN` |

两份都已包含关键项：
- `client_max_body_size 20m;` —— **不加必然 413**
- `location /api/` → `proxy_pass http://127.0.0.1:5183;`（不带尾斜杠，原样透传 `/api` 前缀）
- `proxy_read_timeout 120s` + `proxy_request_buffering off` —— 大图上传/大 JSON 提交
- 单页应用 `try_files $uri $uri/ /index.html`（react-router 刷新不 404）

```bash
sudo cp 项目里的 dd.atc1215.cn.conf /etc/nginx/sites-available/
sudo ln -s /etc/nginx/sites-available/dd.atc1215.cn.conf /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

**前端配套**（`flight-dispatch-system/.env.production` 已就绪）：

```ini
VITE_API_BASE=/api          # 同源相对路径，跟着 nginx 走
```

```bash
pnpm build                  # 产出 dist/
scp -r dist/* root@服务器IP:/var/www/dd.atc1215.cn/dist/
```

### 安全组 / 防火墙

- 阿里云安全组：**只需放行 80 / 443**。
- **不建议**把 5183 开到公网：后端无鉴权，任何知道 IP 的人都能读写删检查单。确需直连再单独放行，并限制来源 IP。
- 服务器防火墙：`sudo ufw allow 80,443/tcp`（或宝塔面板放行）。

## 八、常见故障对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `pm2` 一启动就退出，日志报 `Cannot find module nodemon` | 用了旧的 `npm start`（nodemon） | 用 `pm2 start server.js`，已修 package.json |
| `curl /api/manual-fips` 500，日志 `column "uuid" does not exist` | 表是靠旧代码建的，缺 uuid 列 | 重新 `bash import_flight_dispatch.sh`，或手动 `ALTER TABLE manual_fips ADD COLUMN uuid VARCHAR(64) NOT NULL DEFAULT gen_random_uuid()::text;` |
| 模板接口返回空数组 | `data/checklists/` 没上传或中文目录名乱码 | 重传 `data/`，用 `tar` 而非 Windows 压缩工具 |
| 上传截图报 **413** | nginx 体积限制 | 确认配置里有 `client_max_body_size 20m;` 并 reload |
| 上传报 415 | Content-Type 不在白名单 | 只支持 png/jpg/webp/gif/bmp/tif |
| 接口全 404 | nginx 反代路径写错 | `location /api/` + `proxy_pass http://127.0.0.1:5183;`（**不带**尾斜杠） |
| 启动日志 `检查/创建数据库失败` 但服务照常起来 | PG 连不上（密码错/未启动） | 代码刻意不阻断启动；改 `.env` 后 `pm2 restart v5-dispatch` |
| 导入时 `unrecognized configuration parameter "transaction_timeout"` | 用了未经兼容处理的 pg_dump 18 原始文件 | 用 `flight_dispatch_full_20260923.sql`（已注释该行） |
| 导入时 `function gen_random_uuid() does not exist` | PG ≤ 12 且没装 pgcrypto | `psql -d flight_dispatch -c "CREATE EXTENSION pgcrypto;"`，脚本已自动尝试 |

## 九、上线后待办 / 已知遗留

1. **后端完全没有鉴权** —— 所有接口都是 `@access 公开`，包括增删改检查单。公网暴露前建议至少加一层简单 token（nginx `auth_basic` 或后端中间件），否则等于把数据敞开。
2. **删除检查单不会级联删图片** —— `data/uploads/` 里的截图是现场证据，刻意不随记录删除。长期会积压孤儿文件，需要定期人工清理，或后续加一个"标记删除 + 归档"策略。
3. **`flight_info` 表是历史遗留** —— 后端代码没有引用，确认无用后可从库中删除（或保留作历史归档）。
4. **备份策略** —— 至少要覆盖：`data/uploads/`（图片证据，磁盘上唯一副本）+ 数据库 `pg_dump` 定时导出。
5. **日志** —— 当前 `morgan("dev")` 是彩色开发格式，生产可换 `morgan("combined")` 方便落盘分析；PM2 日志建议配 `pm2-logrotate` 防爆盘。
