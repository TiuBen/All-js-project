## 设计决策（与需求字面有出入之处，都做了取舍）

- **编辑态下被取消勾选的列不立即消失，而是压暗**（表头 label 加删除线，单元格 `opacity-25`）。
  原因：checkbox 就在表头里，列一旦整列消失就没法再勾回来。所以编辑期只做「视觉标记」，点**确认**后该列才真正从表格移除。
- **编辑态禁止点表头排序**（`onClick` 置空），避免与勾选/调序冲突。
- **草稿不落盘**：persist 的 `partialize` 只存 `tableHeaders`，`draftHeaders` / `editingView` 是纯 UI 态。否则"改了没确认"的状态会被当成已保存配置。

## 踩到的两个坑（下次直接绕开）

1. **zustand v5 persist 默认读的是 `window.localStorage`**（middleware.mjs 里写死 `createJSONStorage(() => window.localStorage)`），不是裸 `localStorage`。在 Node 里跑 store 单测必须 stub `globalThis.window = { localStorage }`，只 stub `localStorage` 会静默降级（persist 直接 return，`store.persist` 都拿不到，只打一行 "the given storage is currently unavailable"）。
2. **`normalizeHeaders` 早期版本用「显式 colOrder ?? 声明下标」再排序**，遇到**部分列的缓存**会碰撞（缓存只给了 1 列 colOrder:0，声明下标也是 0 的第一列就撞车），排序结果随机。改成「有 colOrder 的先按其排序，没有的按声明顺序排在最后，最后统一重编号 0..n-1」。

## 追加：视图切换按钮语义修正（FipsPage）

**改法**（`src/pages/FipsPage/FipsPage.jsx`）：
- 把散在组件内的 `viewModeMeta` 提到**模块作用域**，拆成两个常量：
  - `VIEW_CYCLE = { all: "in-left", "in-left": "out-left", "out-left": "all" }`（当前态 → 下一态）
  - `VIEW_META = { all | in-left | out-left: { label, icon } }`（只描述单态，不含方向语义）

### 核心设计：跨表 uuid 唯一（PG 没有跨表唯一约束）
`src/db/flightUuidSchema.js`（新）
- `flight_uuid_registry(uuid PK, source_table, created_at)` —— 全局**名字簿**。
- `BEFORE INSERT OR UPDATE` 触发器 `flight_uuid_claim()`：想用某 uuid 必须先在名字簿占位（INSERT）。撞名分两种：
  - **同表重复** → `RAISE EXCEPTION`（真 bug，打断事务）
  - **跨表占用** → 静默 `gen_random_uuid()` 换号重试，调用方无感
  - UPDATE 且 uuid 未变 → 早退（避免自我冲突）；UPDATE 换了 uuid → 删旧名字
- `AFTER DELETE` 触发器 `flight_uuid_release()` → 删名字（否则名字永久泄漏）
- `registerExisting()` 用 `ON CONFLICT (uuid) DO NOTHING` 幂等登记存量
- 导出 `REGISTRY_TABLE` / `UUID_TABLES = ['fips','manual_fips','ecyilang']`

`src/db/flightRefSchema.js`（新）—— 挂靠列与匹配口径
- `flight_no_variants(text) → text[]`：剥 `/xxx` 后缀、拆前缀+数字，经 `airplane_company_name_code` 做 **IATA↔ICAO 互换**，去重。匹配时用数组交叠 `&&`，所以「台账写 CSS122、fips 写 O3122」也能对上（实测：CSS122↔{CSS122,O3122}、GTI8608↔{5Y8608,GTI8608}、K4866↔{CKS866,K4866}）。
- `try_date(text) → date`：宽松转换，脏数据返回 NULL 不报错。
- `base_flight_uuid(text)`：`regexp_replace(btrim(p), '-[da]$', '')` —— **关键坑**，见下。
- `resolve_flight_uuid(callsign, date)`：**唯一的匹配口径**，回填与运行时共用。排序 `ORDER BY dist, prio, fuuid`：
  - `dist` 日期距离（**只当打平手的参考，不做硬条件**）
  - `prio` 来源优先级 `ecyilang(1) > fips(2) > manual_fips(3)`
  - `fuuid` 最后定序 → 保证**确定性**

### 踩到的大坑：ecyilang 的航段后缀
ecyilang 一行 = 去程+回程，前端拆成两个航班对象，键是 `<uuid>-d` / `<uuid>-a`，而表里只存裸 uuid。
→ 若不剥后缀，`checklist_records` 里带后缀的值会被孤儿清理**误删**，`syncChecklistUuid` 也找不到宿主行。
**修法**：加 `base_flight_uuid()`，孤儿清理与 `syncChecklistUuid` 两边都先过一遍；`flightService.getFlightByUuid` 在 JS 里剥后缀并优先匹配对应航段。

### 其它关键点
- **日期区间不重叠**：ecyilang 只有 09-29~10-02，生鲜台账是 09-01~09-29 → 按「同一天」匹配是**不可能**的，所以日期只能当 tiebreaker。这是 `resolve_flight_uuid` 设计的直接原因。
- **`special` 就是生鲜台账**（50 条来自 `生鲜航班调度节点.xlsx` 的 29 个 sheet）。所以 `/api/fresh-air-cargo` 返回 50 条是**正确口径** —— 进台账即生鲜航班，不是 bug。
- **差点静默丢数据**：原 `fresh_air_cargo` 那 1 行（`source_id=05b178ad…` → manual_fips `BBB11`）迁移时会丢。补了一条 `special_records`（id=51，callsign BBB11，belongTime 2026-08-31，`nodesTime={'freshMark':{}}`）。
- **两表并存事故**：迁移后 `special` 与 `special_records` 同时存在（49 vs 50 行），FULL JOIN 比对 `(callsign, belongTime)` 确认新表是正确副本，只有待删的 O3190 一行差异 → 事务里显式 drop 掉旧表；同时**加固代码**：`renameLegacyTable` 检测到两表并存只打 warning 不动作（避免静默丢数据）。
- **约束名遗留**：`RENAME COLUMN` 不改约束名，`checklist_records` 会留下 `checklist_records_flight_id_not_null` 这种指向已不存在列的怪名。已在库里改名 + 在 `flightRefSchema.js` 加了幂等 `DO` 块自动修。

- **Windows 控制台编码**会把 SQL 里的中文字面量/别名搞坏，psql 校验一律用 ASCII 别名与 ASCII 条件。

→ 裸数字不是 uuid → **孤儿清理每次启动都跑** → 下一条重启时这条记录被**静默删除**，用户填好的整份检查单凭空消失。**无任何报错、无日志、无痕迹**。

**验证（事务内，已 ROLLBACK）**：`INSERT ... flight_uuid='5'` → 存入 `'5'`，孤儿谓词 `would_be_deleted_next_boot = 1`。确认隐患真实存在。

**修法（两层，缺一不可）**：
1. **后端加关口**（`flightService.resolveFlightRef(ref)`）：写入前把「航班引用」解析成真 uuid ——
   - 真 uuid（可带 ecyilang `-d`/`-a` 后缀）→ 并校验**确实存在于三张表之一**（拼错的 uuid 不算合法）
   - `fips-<id>` → 查 `fips.id`；`manual-<id>` / 裸数字 → 查 `manual_fips.id`
   - 解析不出来 → **`createRecord` 直接 400**（`flightId（X）对不上任何航班…无法建立检查单`）
   - 原则：**宁可写入时报错，绝不放行非法值**（报错能看见，静默删除看不见）
2. **前端发正确值**（`buildPayload`）：`flightId: s.flight.uuid || s.flight.id`。

**端到端实测**（临时实例 5186）：`"5"` → 解析成 manual_fips#5 的 uuid ✓ · `"999999"` → 400 ✓ · `"abc-xyz"` → 400 ✓ · `"fips-10209"` → 解析成 fips uuid ✓ · 新建后 `orphans=0` ✓ · 来源表 `checklist_uuid` 正确回写（manual_fips#5→38、fips#10209→39）✓ · 测试记录已删（记录数回到 8，checklist_uuid 复位 NULL）。

**教训**：把「列改名」这类机械重构做完后，**必须回头查一遍写入路径**——读路径的字段改名一眼能看出，写路径的「值语义变了」（数字 id → uuid）不会报错，只会在下次重启时静默毁数据。凡是「有启动时清理/迁移逻辑」的表，写入端都要配一个**前置校验**，否则清理逻辑会变成数据毁灭器。

**另一个坑**：`curl` 在本机要加 `--noproxy '*'`，否则系统代理会拦截 127.0.0.1 请求返回 502 `upstream connect failed`（看起来像后端挂了，其实是被代理挡了）。

### 技术要点：PG 没有「原地改列序」
唯一办法是重建表。写了 `migrate-uuid-column-position.mjs`（幂等、支持 `--dry`）：
```
释放序列归属 → 旧表改名 _old → 按新列序 CREATE TABLE → INSERT..SELECT 拷数据
→ DROP 旧表 → 重建 约束/索引/触发器/注释 → 归还序列归属 → setval
```
全程**单事务**，提交前自动校验：行数 + 全表指纹 + 第 2 列 + 触发器数 + 名字簿 + 函数齐全。

踩到的坑：
1. **PG 18 把 NOT NULL 也登记成 `pg_constraint`（contype='n'）** —— 我按约束清单再 ADD 一次，
   直接报 `cannot create not-null constraint "fips_id_not_null" on column "id"`。
   修法：约束只取 `contype IN ('p','u','c','x')`，NOT NULL 内联在列定义里出。
2. **序列会被连带删掉**：`id` 的 `serial` 序列是 `OWNED BY 表.id`，`ALTER TABLE RENAME` 后归属跟着走，
   `DROP TABLE _old` 会**把序列一起删**（新表默认值随即指向不存在的序列）。
   修法：drop 前先 `ALTER SEQUENCE ... OWNED BY NONE`，建完再 `OWNED BY 新表.id`。
3. **指纹不能直接用 `row::text`** —— 那是按列顺序拼接的，列序一变哈希必变，等于没校验。
   改用 `to_jsonb(row)::text`：jsonb 会把键按 (长度, 字节序) 归一化，**列序无关**，
   所以「哈希相同」能真正证明数据没变。
4. `pg.Client.release()` **返回 void**，写 `c.release().catch()` 会在错误处理分支里再抛 TypeError，
   把真正的错误盖掉。

## 二、主键全量 UUID 化 + 名字簿下线（同日，需求：「去掉 flight_uuid_registry，让所有表 id UUID PRIMARY KEY DEFAULT gen_random_uuid()」）

### 需求与两处确认
用户要求删掉 `flight_uuid_registry` 名字簿，改成「所有表 `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`」
—— 靠随机 uuid v4 碰撞概率可忽略来天然满足跨表唯一，不再强制。
追问后确认两点：
1. 冗余的独立 `uuid` 列（fips / manual_fips / ecyilang）→ **合并进 id**，不保留；
2. 「所有表」→ **只改 5 张业务表**，两张码表（airport_name_code / airplane_company_name_code）保持整数自增。

### 数据库改动（脚本 `migrate-pk-to-uuid.mjs`，已跑通并提交）
- 五张业务表 `id` → `uuid NOT NULL DEFAULT gen_random_uuid()`（由旧 `uuid` 列的值搬过来，
  所以 `flight_uuid` 存量引用**零重映射**）
- `checklist_records.id` 是新建的 uuid → 必须先建临时映射表 `_clmap(old_id→new_id)`，
  再据此重写 `fips/manual_fips.checklist_uuid`
- 删掉三张表的独立 `uuid` 列 + `fips_uuid_key` / `manual_fips_uuid_key` / `ecyilang_uuid_key`
- 删掉 `flight_uuid_registry` 表 + `flight_uuid_claim()` / `flight_uuid_release()` + 6 个触发器
- 5 个整数自增序列（`fips_id_seq` 等）随之消失
- 保留 4 个工具函数：`flight_no_variants` / `try_date` / `base_flight_uuid` / `resolve_flight_uuid`

### 发现的坑（都是这次才暴露的真缺陷）
1. **旧代码把 `uuid` 列又加回来了** —— 迁移脚本删完之后，只要有任何一次进程在
   **旧版 initDb()** 上启动，那份 `ALTER TABLE ... ADD COLUMN uuid` 就会把列重新加上
   （落在最后一列、值是全新的随机 uuid、与 id 无关），库变成「id 已是 uuid + 又一个假 uuid 列」的混合态。
   → 修法：在 `schema.js` 里新增 `dropRedundantUuidColumns()`，**并进 initDb() 做幂等收敛**，
   任何时刻被加回来都会在下次启动清掉。实测：跑 initDb 两次结构稳定、行数不变。
2. **`syncChecklistUuid` 里 `WHERE id = base_flight_uuid($1)` → `操作符不存在: uuid = text`**。
   `id` 从整数变成 uuid 后不能再跟 text 比。修法：`WHERE id = $2::uuid`，
   并且**必须用两个占位符** —— `$1` 是 text（喂给 `base_flight_uuid` 做文本比对）、
   `$2` 是 uuid（比主键）；同一个参数被推断成两种类型 PG 会直接拒绝。
   （测试里给 ecyilang 航班建检查单就打在这里，500。）
3. **`ecyilang` 没有 `checklist_uuid` 列**，而 `syncChecklistUuid` 原来遍历 `FLIGHT_TABLES`
   （含 ecyilang）→ 给 ecyilang 航班建检查单必炸 `column "checklist_uuid" does not exist`。
   前端 `config/dataSource.js` 的 `VITE_FLIGHT_SOURCE=ecyilang`（`pnpm testWW`）是真实可达的数据源，
   所以是活 bug。修法：新增 `CHECKLIST_LINK_TABLES = ['fips','manual_fips']` 专用于回写，
   `FLIGHT_TABLES` 只留给「拿 id 比对」的场景（孤儿清理、反查航班），并加注释说明区别。
4. **`specialService` 的 INSERT 报「对于参数$1,推断出不一致的类型」**（既有缺陷，不是这次改出来的）：
   `VALUES ($1, $2, $3, resolve_flight_uuid($1, $2))` 里 `$1` 同时被 `callsign` 列（varchar）
   和函数形参（text）定型，PG 不允许同一占位符有两种推断类型。
   修法：函数调用改用独立占位符 `$4`（值同 callsign），`createRow` / `upsertByKey` 两处都改。
   → 这也解释了为什么 `/api/special/upsert` 之前一直 500。
5. **`createRecord` 不是事务性的**：INSERT 先 COMMIT，随后 sync 抛错 → 接口回 500
   但记录**已经落库**（这次冒烟测试就留了一条残留，靠手动删掉）。
   本次未改（改动面涉及 create/update/delete 三个函数改为共用 client），**属已知待办**；
   在 sync 修好之后触发条件已基本消失。

### 排序的连带影响
`ORDER BY id` 原本等于「Excel 导入顺序」。主键换成随机 uuid 后这个隐含顺序消失，
试了 11 种候选排序键组合，用逆序数比对都还原不出原顺序（最好的 `in_out_time` 逆序率 106%，比随机还差）
→ 用户确认**改成按时间排**：
- `fipsService`：`sobt NULLS LAST, atot NULLS LAST, flight_no`（升序）
- `manualFipsService`：`aldt NULLS LAST, sobt NULLS LAST, flight_no`
- `ecyilangService`：`批次日期, COALESCE(d_plan_time, a_plan_time) NULLS LAST, 航班号`
- `specialService` / `freshAirCargoService`：去掉拿 uuid 当排序键的写法（改成业务键）
- 前端 `FipsPage` 只在点表头时客户端排序 → 默认顺序完全由后端决定

### 接口约定（保持前端零改动）
